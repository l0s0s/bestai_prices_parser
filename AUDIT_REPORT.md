## Новый конкретный баг: Azure OpenAI указывает на Amazon Bedrock

`app/sources/apirank.py:12`:
```python
"azure-openai": "https://aws.amazon.com/bedrock/", # or azure
```
Проверил в реальных данных после прогона — подтверждено:
```
{'name': 'Azure OpenAI', 'domain': 'amazon.com', 'website_url': 'https://aws.amazon.com/bedrock'}
```
Это явная опечатка (похоже, скопировали строку `amazon-bedrock` при добавлении новых записей в карту и не поправили значение, комментарий `# or azure` выдаёт незавершённое решение). Результат — в данных Microsoft Azure OpenAI Service дословно приписан домену Amazon. Тривиально чинится одной строкой (`"azure-openai": "https://azure.microsoft.com/en-us/products/ai-services/openai-service"` или похожий актуальный URL), но раз уж заметил — обязательно нужно поправить, это ровно тот тип ошибки ("код выдаёт неверный, но правдоподобный факт"), который был центральной темой всех прошлых аудитов.

## Резолюция HTTP-редиректов вернулась и стала параллельной ✅

`app/services/provider_discovery.py::resolve_final_domain` — снова делает `httpx.Client(...).head()` с `follow_redirects=True, max_redirects=2` (ТЗ Шаг 2 выполняется). При этом `normalize_and_deduplicate` теперь прогоняет резолюцию через `ThreadPoolExecutor(max_workers=20)` — разумное решение проблемы производительности, которая, судя по всему, и была причиной удаления этой логики в v3 (163 последовательных HTTP-запроса были бы медленными). Таймаут на резолюцию срезан до 2 секунд — с параллелизмом это разумный компромисс. Отдельно проверил на реальных данных: домен `nvidia.com` в этом прогоне корректно "поймал" 2 записи из одного каталога под одним `provider_id` — значит объединение дублей по итоговому домену реально работает на живых данных, а не только в тестах.
